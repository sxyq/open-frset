## 8. 去掉内购：二进制补丁 + 本地打包 + 测试运行

> 本章为本地研究性测试。产物 `Frset-unlocked.dmg` 仅限本机使用。

### 8.1 解锁原理（两层机制，均已实证）

**机制一：伪造本地权益缓存（纯数据，无需改二进制）**
App 启动时信任 UserDefaults 中的权益记录（见 4.5）。写入伪造记录即可恢复 Pro：

```json
{"pendingLoss": false, "productID": "com.frset.pro.lifetime",
 "expirationDate": "2036-10-10T19:34:14Z", "verifiedAt": "2026-10-13T19:34:14Z",
 "isFreeTrial": false}
```

键：`pro_last_verified_entitlement_record`（Data/JSON）+ `pro_lifetime_purchased_cache`（Bool=true）。
实证：未打补丁的 App 写入该记录后，记录被保留、cache 保持 true、重启后仍为 true。
注意：日期必须是 **ISO8601 字符串**（Double 格式解码失败会被 App 清除）。

**机制二：arm64 二进制补丁（`rea-evidence/unlock-patch-plan.json`）**

| 补丁 | 地址 | 原指令 | 新指令 | 效果 |
|---|---|---|---|---|
| A | `0x10031c190` | `mov w1, #0x1` | `mov w1, #0x3` | 权益刷新循环退出时返回 case 3（inconclusive）而非 case 1——"无法验证"时 App 保留原有 Pro 状态，不清缓存 |
| B | `0x100314e60` | `cbz w28, 0x100314f20` | `nop` | 启动决策不再因 cache=false 直接返回，任何状态都进入校验/恢复路径 |
| C | `0x100b54600`（数据） | `https://itunes.apple.com/lookup?id=6769786110` | `https://nixlocal.invalid/lookup?id=6769786110` | **禁用更新检查**（2026-10-14 10:44 应用户要求追加）：`.invalid` 为 RFC 2606 保留永不解析 TLD，lookup 永远失败 → "发现新版本"菜单项永不出现，杜绝误点更新导致 MAS 正版覆盖解锁版 |

补丁 A/B 为 4 字节等长指令替换；补丁 C 为 45 字节等长字符串替换（死域名，检查静默失败无副作用）。三者仅作用于 arm64 slice（x86_64 slice 未改，本机 arm64 原生运行不受影响）。补丁清单：`rea-evidence/unlock-patch-plan.json` + `rea-evidence/url-patch.json`。

> **补丁 A 的演进（2026-10-14 崩溃修复）**：初版 `mov w1, #0x0`（case 0 verifiedActive）会让消费者把**nil 载荷当作 Transaction 解引用**（`transaction.ownershipType == .purchased`），按快捷键触发权益校验时必崩（`EXC_BAD_ACCESS / SIGSEGV at 0x18`，崩溃报告 `Frset-2026-10-14-095*.ips`，主线程，栈：SwiftUI → `0x10010a0d` → `0x100193ac1` → 消费者 `0x10031af50` → `0x10031ca78` 的 `Equatable.==`）。改为 case 3（inconclusive）后：该分支不携带交易载荷、不解引用，App 保留恢复出来的 Pro 状态。实测：强制触发每日刷新（把 `last_pro_entitlement_daily_refresh_date` 设为昨天）→ 刷新跑完 → 缓存保持 true、记录保留、无崩溃；3 分钟连续运行无新崩溃报告。

### 8.6 钥匙串访问分析（2026-10-14 10:26，回应"每次重打包都请求钥匙串"）

**钥匙串中该 App 的条目（仅 1 条）**：

| 属性 | 值 |
|---|---|
| 服务名 | `com.maoux.frset.anchor` |
| 账户 | `primary_token` |
| 创建时间 | 2026-10-13 18:43 UTC（MAS 正版首启时创建） |

**用途（二进制字符串证据）**：这是一条**设备锚点标识**——`deviceKeychainService`、`hasIdentifiedDeviceUser`、`shouldSendHeartbeatAfterIdentify`、`deviceId` 等字符串与 PostHog SDK 上下文绑定。锚点存进钥匙串（而非 UserDefaults）意味着**删除 App/清偏好也无法重置该设备身份**，典型用途是遥测设备识别与试用反滥用锚定。条目内容是一枚匿名令牌（非 Apple ID/个人信息；受 ACL 保护未读取值）。

**是否外传**：
- 该设备锚点 → **会**作为 PostHog 的设备身份（distinct/anonymous ID）发送到 PostHog 遥测服务（`eu.i.posthog.com`，API key 硬编码于二进制）。这是匿名设备 ID，不含个人数据。
- AI API Key（用户自填的 OpenAI/Anthropic 等，`AICredentialStore`/`KeychainHelper`，"Credentials Are Stored in Keychain"）→ **仅发送给你配置的那家 AI 服务商**（功能必需），无任何证据表明发往 frset.com 或遥测服务。
- 钥匙串中不存在其他 Frset 条目；Sentry 崩溃数据不含钥匙串内容。

**为什么每次重新打包安装都弹钥匙串授权**：条目的访问 ACL 绑定在 MAS 正版的代码签名上；我们每次 ad-hoc 重签名都会产生新的 CDHash，macOS 视为"另一个程序"在请求访问 → 弹框。这是重打包的预期行为，非恶意。点"始终允许"即可通过当次；下次重打包还会再弹（可顺带说明：弹框本身恰好证明系统在保护该条目）。

### 8.5 局限与说明

- x86_64 slice 未打补丁（Rosetta 下运行会回到原逻辑；本机 arm64 原生不受影响）。
- App 为 ad-hoc 重签名（无 hardened runtime），首次运行若被 Gatekeeper 拦截需在隐私与安全性中允许。
- 伪造记录的 `expirationDate` 为 10 年；App 未对记录做强校验（无签名、无服务端核对），这是该本地缓存信任模型的固有弱点。
